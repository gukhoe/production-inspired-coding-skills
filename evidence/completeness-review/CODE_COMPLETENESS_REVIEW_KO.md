# 코딩 완성도 추가 검토: 정확한 출력과 유지보수 준비도는 다르다

## 결론

**90개 최종 코드는 모두 실제 계산 로직을 갖추었고, 요청된 입력과 출력 범위에서는 완성된 작은 Python 프로그램입니다. 그러나 이는 운영용 소프트웨어 완성도 100%를 뜻하지 않습니다.**

기존 실행 검증에 이어 코드를 추가로 읽어 보니, A/B/C 모두 계산 함수와 예제 실행이 분리되어 있고 인자를 받아 결과를 반환하는 재사용 구조를 갖췄습니다. **C만 구현이 더 완전하거나 구조가 더 좋은 패턴은 확인되지 않았습니다.** C에서는 요구사항·범위·실행법 문서가 더 자주 작성됐지만, 그 문서의 조건이 실제 방어 코드로 연결되지 않은 사례도 있습니다.

이 자료는 **실험 종료 후 추가한 정적 AI 코드 리뷰**입니다. 새로운 생성 실험이나 완전한 생산환경 검증이 아닙니다. 기준을 재검토 전에 고정하고, 코드를 무작위 ID로 가려 그룹을 숨긴 상태에서 검토했습니다. 코드의 문체·문서는 처치를 드러낼 수 있고 조정자는 기존 결과를 알고 있으므로 완전 맹검으로 주장하지 않습니다.

## 무엇을 필수로 봤는가

- 필수: 실제 계산, 요청된 결과/선정/순위 출력, 실행 가능한 Python 구성. 제공 입력값을 소스에 넣는 것은 허용하며, 정답만 상수로 출력하는 것과 구분했습니다.
- 선택적 개선: 비례적인 구조와 가독성, 함수 재사용, 오류/경계 처리, 자체 테스트의 의미, 사용/정책 문서.
- GUI·DB·웹 API·패키징·CI·특정 함수명·JSON·CLI를 요구하지 않았습니다. 이런 기능이 없다는 이유로 감점하지 않았고 코드량이나 문서량 자체에 가점을 주지 않았습니다.
- S/R/E/T/D의 0–2 평정은 근거를 찾기 위한 질적 분류입니다. 총점을 합산하거나 이를 완성도 백분율·우열의 통계적 근거로 사용하지 않습니다. 특히 E는 업무별 난이도와 주관적 경계가 있어 원문 근거를 우선해야 합니다.

마지막 네 행은 **코드에서 관찰된 기능의 유무**이며 많을수록 좋다는 점수가 아닙니다. 단순 재고 산술과 OEE의 적정 검증은 다릅니다. 별도 문서가 없어도 함수 docstring·명료한 예제로 사용법이 충분할 수 있고, 표준 라이브러리가 오류를 처리하므로 자체 raise가 없다고 오류 처리가 전혀 없다는 뜻도 아닙니다.

## 구체적 코드 증거

### 문서가 검증 코드와 같지는 않음

- `runs/r3_T05_C/production_quality.py:3`은 produced > 0 및 defective 범위를 명시하지만 `:9–13` 계산 함수는 입력 검사 없이 나눗셈·뺄셈을 합니다. produced=0에서 나눗셈 오류, defective>produced에서 음수 양품이 발생할 수 있습니다. 이는 정적 코드로 확인한 재사용 위험이며 제공 입력의 실패가 아닙니다.
- 같은 과제의 `runs/r1_T05_A/quality.py:6–11`과 `runs/r2_T05_B/quality.py:6–13`은 정수 여부·양수 분모·불량 수량 범위를 명시적으로 검사합니다. 반대로 C는 정상·전량 불량·무불량 테스트를 더 꾸준히 남겼습니다. 한 측면만으로 전체 완성도를 판단하면 안 됩니다.

### 숫자 반환과 사용자에게 보이는 출력은 별도 품질

- `runs/r3_T06_A/invoice_balance.py:6–10`은 Decimal 잔액을 반환하지만 `:17–19`의 표시 형식은 소수점 이하를 버리는 반올림입니다. 향후 소수 금액을 넣으면 반환값과 사람이 보는 금액의 정밀도가 다릅니다. 원 입력은 정수 금액이므로 기존 통과 판정은 유지됩니다.
- `runs/r1_T06_C/invoice_balance.py:19–21`은 요청에 통화가 없는데 원 단위를 붙였습니다. 계산은 맞지만 재사용 시 통화 가정을 명확하게 해야 합니다.

### 경계 처리도 구현별 차이가 있음

- `runs/r2_T09_B/oee.py:13–19`는 주요 범위를 검사하지만 NaN을 거부하는 유한 수 검사가 없어 비정상 수치가 결과에 전파될 수 있습니다.
- `runs/r1_T09_A/oee.py:6,15`는 반환 비율 0~1이라고 설명하지만 성능률이 1을 초과할 수 있습니다. `runs/r3_T09_C/oee.py:4–5`도 0~1이라는 설명과 100% 초과를 보정하지 않는다는 설명이 함께 있습니다. 자동 상한 보정을 요구하는 것이 아니라 문서 계약을 실제 동작과 일치시키라는 뜻입니다.

### C에서 확인되는 긍정적 개선

- `runs/r1_T03_C/README.md:3–20`은 입력·공식·보존 관계·범위와 실행/테스트 명령을 함께 제공합니다. 다른 사람이 인수해 사용하는 데 실질적으로 도움이 되는 자료입니다.
- C의 별도 문서는 총 18개 산출물에 있으나 이것만으로 구현 정확도, 오류 방어, 테스트 품질 개선을 입증하지는 않습니다. A/B도 모든 산출물에서 재사용 함수와 main 보호 구조를 갖췄습니다.

## 이번 결과로 말할 수 있는 범위

**기본 작은 프로그램 완성도는 세 그룹 모두 양호하고, C는 요구사항·사용설명의 흔적이 더 뚜렷합니다. 그러나 문서화가 실제 오류 방어와 충분한 검증으로 일관되게 이어졌다고 볼 수 없고, 전체 코딩 완성도의 우월성은 확인되지 않았습니다.**

이 결론은 10개의 짧은 산술/날짜 과제와 3반복의 최종 소스에만 적용됩니다. 실무 유지보수, 변경 후 회귀, 잘못된 입력 복구, 설치·배포·성능·보안·사용자 경험은 이번 요구사항에 없고 충분히 시험하지 않았으므로 생산용 준비도라고 부르지 않습니다.

이번 추가 리뷰는 원본 소스를 변경하거나 새로 생성하지 않았습니다. 300초 초과 3건도 최종 산출물 정적 검토에는 포함했으며, 시간 내 완성 여부와 분리해야 합니다. 기존 토큰 미계측·모델 revision 미확인·공유 파일시스템 한계도 그대로입니다. 리뷰에서 발견한 문제를 참가자에게 돌려 수정시키지 않았습니다.
