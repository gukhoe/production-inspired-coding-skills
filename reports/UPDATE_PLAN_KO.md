# SKILL.md 업데이트 준비안

상태: 준비 완료, 원본 16개 `SKILL.md`의 내용 수정은 미적용.

목적은 제조업 생산·품질 프로세스를 코드 개발의 실행 절차로 바꾸는 것입니다. 제조업 분야의 그림·소프트웨어만 만들거나, 제조업 용어를 더 많이 사용하는 것이 목표가 아닙니다.

## 적용 순서

1. 원본 스킬과 첨부 자료를 새 저장소의 기준 버전으로 고정합니다.
2. 잘못된 통과를 허용하는 평가기와 설명문을 v2 작업에서 먼저 정정합니다. 원본 기록은 보존합니다.
3. SOR → PFMEA → Poka-Yoke → Control Plan → MSA의 연결을 최소한으로 개선합니다.
4. 동일 과제에 대해 스킬 적용 전후의 실제 구현·실행 결과를 비교합니다. 코드·문서 분량은 참고치만 사용합니다.
5. 유용한 행동 변화가 확인된 수정부터 반영합니다. 나머지 스킬은 해당 상황의 검증 사례가 있을 때 개선합니다.

## 16개 스킬별 준비사항

| 스킬 | 관찰한 보완 지점 | 최소 수정 방향 | 확인할 행동 |
|---|---|---|---|
| `sor-requirements` | `Never infer unstated behavior`가 사소한 판단까지 막을 수 있음 | 결과에 영향을 주는 정책은 확인하고, 낮은 위험의 선택은 가정을 기록하고 진행; 핵심 계약을 테스트에 연결 | 단위·정밀도·범위가 구현과 일치하고 불필요한 확인 질문 감소 |
| `pfmea-risk` | 위험을 써도 통제 구현 누락 가능 | 각 중요 위험에 통제 위치·검사·관측 결과를 짧게 연결; 5개는 우선순위 안내로 사용 | 문서에 쓴 핵심 실패가 실제 코드/테스트에 반영 |
| `poka-yoke` | 예방 도구 나열은 있으나 효과 확인이 약함 | 잘못된 입력/상태가 통제 전 실패하고 통제 후 거부되는 의미 있는 검사 | 허용 입력은 유지하고 관련 오류만 방지 |
| `control-plan` | `Never rerun`이 MSA 재현 검사와 충돌 가능 | 소스·의존성·설정·입력·환경·외부 상태 변화와 불안정성 조사에 따른 재검증 조건 명시 | 중복 검증과 필요한 재검증을 구분 |
| `msa-test-reliability` | 평가기 허위 통과에서도 필요하나 트리거가 flaky/AI 의견 차이 위주 | 정답 기준 오류, 항상 성공/실패하는 결함 구현을 구별 못하는 검사도 트리거에 포함 | 항상 예외인 구현을 정상 품질로 평가하지 않음 |
| `standard-work` | 본문과 인덱스의 적용 범위가 다름; 완료 기준 과소 설정 가능 | 작업 범위에 맞는 완료 기준과 필수 검사로 종료; 매 작업의 불필요한 의식화 방지 | 작은 작업은 짧게, 필요한 확인은 생략하지 않음 |
| `eight-d-root-cause` | 고정 3회/동일 서명 2회 종료가 진전 중인 진단을 끊을 수 있음 | 같은 가설·같은 조건의 무진전 반복을 중단; 새로운 증거가 있으면 진단 전환 | 원인 재현과 회귀 확인, 인프라 오류 별도 기록 |
| `andon-jidoka` | `unknown environment`가 광범위한 즉시 중단을 유도 | 영향 있는 변경/승격을 멈추고 읽기 조사·격리 재현은 계속; 중단 해제 조건 명시 | 위험 작업은 멈추되 안전한 원인 규명은 지속 |
| `containment` | 브랜치 생성만으로 영향 격리라고 오해 가능 | 개발 변경 격리와 운영 영향 차단을 구분; 근거와 영향을 기록 | 실제 차단 범위만 주장 |
| `ecn-change-control` | 승인된 범위에서도 재승인, 범위 밖 이슈 자동 생성 가능 | 기존 사용자 승인 범위를 존중; 범위 밖 발견은 보고하고 외부 이슈 등록은 요청에 따름 | 불필요한 승인 반복·외부 변경 없이 영향 추적 |
| `first-article` | 대표 1개가 변형 전체를 대표한다고 오해 가능 | 반복 생성의 대표 유형과 중요한 변형을 확인하고 원본 해시 연결 | 결함 템플릿의 대량 확산 방지 |
| `apqp-stage-gates` | 게이트 수가 작업 복잡도보다 커질 수 있음 | 위험에 필요한 게이트만 적용하고 완료 근거·승격 조건 명확화 | 작은 변경에 과도한 절차를 강제하지 않음 |
| `ppap-release-evidence` | 문서 수집이 운영 준비 완료로 오해될 수 있음 | 요구-검사-산출물 버전과 미확인 항목 연결; 승인 권한과 증거 분리 | 검사하지 않은 배포/복구를 통과로 표시하지 않음 |
| `kanban-wip` | 병렬 처리 자체가 목표가 될 수 있음 | 여러 에이전트가 실제 필요하고 허용된 작업에만 적용; 파일 소유·통합 책임 기록 | 충돌 감소와 통합 검사 확인 |
| `line-balancing` | 계측 불가 수치를 추정값으로 채울 가능성 | 측정값과 미계측값을 구분하고 오류율·회귀를 함께 관측 | 시간 단축 때문에 품질 검사 약화하지 않음 |
| `spc-quality-trends` | 과제·모델·환경이 섞인 집계로 추세 오판 가능 | 비교 가능한 조건과 변경 시점을 기록; 혼합 데이터 분리 | 한 번의 성공이나 단순 평균으로 관리 상태 주장하지 않음 |

## 공통 문구와 패키징

- 16개 스킬에 반복되는 Evidence and termination 문단은 역할별 필요성에 맞게 줄이는 후보입니다. 각 스킬의 독립 사용성을 유지해야 하므로 공통 파일 분리는 자동으로 결정하지 않습니다.
- `at most 3 unique error signatures`는 기본 요약 길이로 두고, 원인 규명에 필요한 원시 로그는 추가로 읽을 수 있어야 합니다.
- PASS / FAIL / BLOCKED / UNVERIFIED가 무엇을 나타내는지 검사 단위로 구분합니다. 검사 실패와 도구 사용 불가를 같은 상태로 뭉개지 않습니다.
- `name`, `description`, 폴더명이 맞는지 검사하고, description은 실제 적용 상황을 구분하도록 작성합니다. 실제 스킬 진입 파일은 `SKILL.md`로 유지합니다.
- 선택적 참고자료는 해당 분기에서 필요할 때 읽도록 연결합니다. 기본 스킬 전체를 매번 읽는 운영은 피합니다.
- 추후 설치 경로·라이선스·릴리스 메타데이터는 사용자 배포 방식에 맞춰 정합니다. 이번 초기 보존 단계에서 임의 라이선스나 전역 설치를 추가하지 않습니다.

## 업데이트 후 판단 기준

검사는 실제 요청과 합의한 계약을 기준으로 합니다. 원 요청에 없던 GUI·DB·API·화풍·문서 형식을 사후 필수조건으로 만들지 않습니다.

- 원 요청 충족: 코드가 실행되고 요청 결과가 생성되는가.
- 결함 검출: 중요 실패를 검사기가 실제 잡아내는가.
- 예방 효과: 의도한 통제가 유효 입력을 과도하게 제한하지 않는가.
- 근거 일치: 완료 주장과 실행 로그·파일 버전이 일치하는가.
- 비례성: 추가 과정이 관측된 위험과 변경 규모에 맞는가.
- 비용: 실측 가능한 시간·도구 호출·수정·토큰만 기록하고 미계측은 미계측으로 남기는가.

실제 개선 적용과 새 평가기 제작은 이 준비안을 바탕으로 진행할 다음 작업입니다.
