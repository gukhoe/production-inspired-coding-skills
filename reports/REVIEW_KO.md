# 첨부 분석 재검토 의견

검토일: 2026-11-02 (America/Chicago). 목적: 제조업의 생산·품질·검증 절차를 AI 코딩에 적용하는 스킬의 개선 준비. 이번 작업은 원본 스킬을 수정하지 않습니다.

## 판단

방향은 타당합니다. 요구사항을 SOR로 정리하고, PFMEA로 실패 가능성을 찾으며, Poka-Yoke로 오류를 예방하고, Control Plan으로 검증을 선택하는 방식은 실행 가능한 개발 행동으로 연결할 수 있습니다. 다만 **제조업 용어를 붙였다는 사실, 문서를 많이 만들었다는 사실, 테스트를 적게 실행했다는 사실만으로 코딩 품질 향상을 주장할 수 없습니다.**

개선의 중심은 `요구사항 → 위험 → 구현된 예방책 → 실제 검사 → 결과 근거`의 연결입니다. 작은 작업에는 필요한 부분만 적용하고, 긴 절차를 수행했다는 이유로 가점을 주지 않는 것이 적절합니다.

- 리뷰 90건의 고유 실행 ID와 과제×그룹×반복 조합이 일치했습니다.
- CSV와 JSON의 핵심 필드·관측 특징, 개별 기록으로 다시 계산한 그룹 집계가 일치했습니다.
- 동결 리뷰 기준의 SHA-256이 일치했습니다.
- 관련 연구 ZIP의 동결 파일 45개, 제공 텍스트 20개, 제출 파일 해시 항목 1,737개가 모두 일치했습니다. 이는 파일 무결성 확인이며 모델 세션 독립성의 인증은 아닙니다.
- 기본 스킬 16개는 새로 첨부된 원본과 실험 스냅샷이 같고, 로컬 `skill-creator` 형식 검증을 16/16 통과했습니다. 형식 통과는 행동 품질 보증이 아닙니다.
- 원 보고서가 문서화·입력 방어·계산 정확도·시간 내 완료를 구분한 것은 적절합니다. S/R/E/T/D를 합산 순위로 쓰지 않은 것도 유지할 가치가 있습니다.

## 우선 수정해야 할 평가 문제

### 1. 오류가 났다는 이유만으로 통과하는 평가기

`benchmarks/abc-v1/tests/hidden_tests.py`의 `throws()`는 ValueError, TypeError, KeyError, ArithmeticError를 모두 통과시킵니다. 문자열 금액을 지원하지 않는 A는 정상 입력에서도 TypeError를 냅니다. 그 동일한 결함이 여러 오류 테스트에서 방어 기능처럼 집계됩니다.

이번에 원본 테스트를 그대로 재실행하여 A=13/18, B=17/18, C=18/18을 재현했습니다. 그러나 **무조건 ValueError를 발생시키는 가짜 구현도 13/18을 통과**했습니다. A의 13/18을 72% 완성도나 오류 방어 수준으로 읽으면 안 됩니다.

추가로 정상 숫자 형식의 입력을 사용하면 A는 수량 0, 수량 1.5, 중복 공급사를 그대로 계산합니다. 원본 테스트에서 이 항목들이 통과했던 것은 적절한 계약 검증의 증거가 아닙니다.

수정 방향: 먼저 유효 입력의 성공을 확인하고, 유효한 기준 입력에서 한 조건씩 바꿔 오류를 검사합니다. 오류 타입 또는 오류 코드와 관련 필드를 확인하고, 항상 실패·항상 성공·고정 답 반환 같은 결함 구현을 평가기가 잡아내는지도 확인합니다. 기존 결과를 덮어쓰지 말고 평가기 v2를 별도 동결해야 합니다.

근거: [실제 재실행 결과](verification/abc-rerun.json), [가짜 구현 및 추가 진단](verification/diagnostics.json), [원본 테스트](../benchmarks/abc-v1/tests/hidden_tests.py).

### 2. 설명문과 실제 결과의 불일치

원본 `results/COMPARISON.md`는 A가 수량 0·소수 수량·공급사 중복·비유한 입력·반올림에 실패했다고 설명합니다. 하지만 원본 JSON과 이번 재실행에서 A가 실패한 5개는 다음입니다.

1. `correct_winner`
2. `correct_total`
3. `tie_deterministic`
4. `no_input_mutation`
5. `rounding_half_up`

따라서 실패 설명은 정정이 필요합니다. 원본은 연구 이력으로 유지하고, 이 재검토 문서에서 오류를 명시했습니다. 입력 불변성 테스트 실패 역시 실제 변형이 아니라 계산 중 TypeError 때문이므로 원인을 구분해야 합니다.

### 3. 반복 실행 시연을 실제 최적화 성과로 확대할 수 없음

기본 스킬의 `benchmark/benchmark.py`는 실행 횟수를 직접 5와 1로 지정합니다. 캐시 키나 무효화 로직을 구현·검증하는 프로그램이 아닙니다. 따라서 실제 에이전트가 중복 검증을 식별했다거나 토큰을 절감했다고 해석할 수 없습니다. 해당 README의 한계 표시는 적절합니다.

## 90건 리뷰의 주요 코드 근거 재대조

90건 전체를 다시 평정하거나 재실행한 것은 아닙니다. 전체 기록·해시를 점검하고, 보고서의 다음 주요 사례를 실제 원본 코드와 정적으로 대조했습니다.

| 사례 | 확인 내용 | 스킬 개선에 주는 의미 |
|---|---|---|
| `r3_T05_C/production_quality.py:3,9–13` | 입력 범위는 문서에 있지만 함수에 방어 검사가 없음 | SOR의 요구조건을 코드 검사 및 테스트와 연결 |
| `r1_T05_A/quality.py:6–11`, `r2_T05_B/quality.py:7–12` | A/B에는 정수·양수·불량 수량 범위 검사 존재 | C가 항상 더 강한 검증을 한다고 가정하지 않음 |
| `r3_T06_A/invoice_balance.py:17–19` | Decimal 계산과 별개로 표시값을 정수로 반올림 | 반환값과 사용자가 보는 출력을 함께 점검 |
| `r1_T06_C/invoice_balance.py:19–21` | 요청에 없는 원 단위를 출력 | 중요한 업무 가정과 원 요구사항을 구분 |
| `r2_T09_B/oee.py:13–25` | 이상 사이클 시간 NaN을 명시적으로 거부하지 않아 전파 가능 | 비교식만으로 비유한 숫자를 모두 거를 수 있다고 가정하지 않음 |
| `r1_T09_A/oee.py:6,15`, `r3_T09_C/oee.py:4–5,30` | 0~1 문서와 100% 초과 가능한 계산이 불일치 | 미지정 상한을 강제하기보다 실제 동작과 계약 일치 |
| `r1_T03_C/README.md:3–20` | 입력·공식·보존 관계·실행법이 함께 제시됨 | 인수인계에 유용한 문서는 유지하되 분량 자체에 가점하지 않음 |

코드는 [연구 코드 근거 폴더](../evidence/study-reference/runs/)에 보존했습니다. 원 보고서의 90/90 필수 통과는 기존 실행 근거에 대한 보고이며 이번에 90개 프로그램을 새로 실행해 얻은 수치는 아닙니다.

C의 별도 문서 18/30, A/B의 0/30은 문서화 차이를 보여줍니다. 명시적 raise는 A/B/C 각각 12/11/6, 유한 수 검사는 4/4/2로 집계됩니다. 업무마다 필요한 방어가 다르므로 이 빈도 자체도 순위표가 아닙니다.

## 스킬 본문에 반영할 핵심

1. SOR에서 중요한 입력·출력 계약과 테스트 가능한 예시를 정하되, 사소하고 되돌릴 수 있는 선택까지 질문하도록 만들지 않습니다.
2. PFMEA에서 발견한 위험마다 구현 통제와 실제 검사 근거를 연결합니다. 위험 목록을 적고 끝내지 않습니다.
3. Poka-Yoke는 경고 문장을 늘리는 대신 관련 오류를 실제로 막는 검사·타입·제약·안전한 기본값을 선택합니다.
4. MSA는 불안정 테스트뿐 아니라 허위 통과를 검출하는 평가기 자체 점검에도 적용합니다.
5. Control Plan은 통과한 검사 재사용의 유효 조건과 재실행 사유를 구분합니다. 불안정성 조사나 환경 변화가 있으면 반복 확인이 정당합니다.
6. 완료는 실행한 검사의 범위 안에서만 주장합니다. 문법 검사, 단위 검사, 시각 확인, 운영 적합성을 구분합니다.
7. 작업 규모에 비례하도록 합니다. 고정된 문서 수·실패 횟수·요약 개수 때문에 필요한 작업을 막지 않습니다.

## 로켓 코딩 비교의 위치

사용자가 요청한 비교는 동일한 로켓 그리기 코드를 독립 A/B/C 조건에서 작성·실행하여 코드와 결과를 보는 것입니다. **제조업처럼 보이는 로켓**을 요구하는 실험이 아닙니다. 앞서 이미지 생성 도구에 스킬 텍스트를 넣어 만든 그림은 코딩 과정을 수행하지 않았으므로 이 비교의 근거에서 제외했습니다.

새 비교는 [실제 코딩 비교](../comparisons/rocket-code/README.md)에 별도로 기록합니다. 그림이 더 화려하거나 코드가 길다고 C의 우월성을 판정하지 않습니다. 이번 한 번의 관찰과 반복해서 검증된 효과를 구분합니다.
